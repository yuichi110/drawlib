# 第1章: AI 開発における作図・ドキュメントの課題

AI によるコード生成やペアプログラミングが日常的になる中、ソフトウェア開発におけるボトルネックは「コードの実装」から「**設計・アーキテクチャの可視化とドキュメントの同期**」へとシフトしています。

## 1.1 設計書と実装の乖離（ドキュメントの腐敗）

AI ツール（Cursor, Claude, Copilot など）を活用することで、プログラムコードは驚異的なスピードでリファクタリングや機能追加が行われます。しかし、システム全体のアーキテクチャ図やシーケンス図、データベーススキーマ図などのドキュメントは更新されずに置き去りにされがちです。

結果として、以下のような問題が発生します:
- **ドキュメントの形骸化**: 「ドキュメントと現行コードのどちらが正しいのかわからない」状態に陥る。
- **オンボーディングの遅延**: 新規メンバーや別の AI セッションが全体構造を正しく把握できない。
- **暗黙知の増大**: 最新の設計意図がコードのコミットログやチャット履歴にしか残らない。

## 1.2 手動 GUI ツールの限界

従来、エンジニアは以下のような GUI ツールを用いて作図を行ってきました:
- draw.io / diagrams.net
- Figma / Miro
- PowerPoint / Google Slides

これらのツールで作成された図版は通常、**PNG や JPEG などのバイナリ画像**としてリポジトリに保存されます。このバイナリ管理には決定的な欠点があります:
1. **Git で差分（diff）が追えない**: どこが変更されたのかプルリクエストで視覚的に追跡できません。
2. **AI Agent が編集できない**: AI はバイナリ PNG の中身を直接編集することができません。図を直すには人間が手動でツールを開いて修正し、再度エクスポートする手間が発生します。
3. **デザインの不統一**: 作成者ごとにフォント、色、線の太さ、余白がバラバラになり、組織としてのドキュメント品質が保てません。

## 1.3 AI に生の SVG や Matplotlib を書かせると破綻する理由

では、AI にコードで図を描かせれば解決するでしょうか？ 多くの開発者が試みて挫折するのが、**生 SVG** や **Matplotlib** の直接生成です:

- **生 SVG の直接生成**:
  - テキストの折り返し計算やフォント幅の算出が難しく、テキストが枠からはみ出す。
  - 矢印やコネクタの座標計算が複雑で、線の交差や位置ずれが多発する。
  - 何百行もの `<path>` や `<rect>` が生成され、人間が保守・レビュー不能になる。
- **Matplotlib の流用**:
  - 本来は学術的な散布図や折れ線グラフのためのライブラリであり、システム構成図やシーケンス図を描くための高レベルなプリミティブ（ノード、グループ、矢印配線、アイコン）が存在しない。
  - 大量のボイラープレートコードが必要となり、AI も構文エラーを起こしやすい。

こうした背景から生まれたのが、Python による **"Illustration as Code"（コードとしての図版）** を実現するライブラリ **Drawlib** です。
